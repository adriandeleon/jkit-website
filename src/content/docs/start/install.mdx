This page installs jkit and turns on its shell hook. It takes a couple of minutes on any system;
pick your operating system below. jkit is a single native binary and needs no JDK to run.

## Install

<Tabs syncKey="os">
  <TabItem label="macOS">
    With [Homebrew](https://brew.sh):

    ```bash
    brew install adriandeleon/tap/jkit
    ```

    `brew upgrade` keeps it current. The macOS binaries are signed and notarized by Apple, so
    Gatekeeper lets them run.

    Without Homebrew, use the `macos-aarch64` (Apple Silicon) or `macos-x64` (Intel) archive; see
    [a plain binary](#any-other-system-a-plain-binary).
  </TabItem>
  <TabItem label="Linux">
    **Debian and Ubuntu: apt.** jkit is published in the
    [Vitrina](https://vitrina-project.dev) apt repository, so `apt upgrade` keeps it current. Add
    the repository once, then install:

    ```bash
    sudo install -d -m 0755 /etc/apt/keyrings
    curl -fsSL https://vitrina-project.dev/vitrina.asc | sudo tee /etc/apt/keyrings/vitrina.asc > /dev/null
    sudo tee /etc/apt/sources.list.d/vitrina.sources > /dev/null <<'EOF'
    Types: deb
    URIs: https://vitrina-project.dev/apt
    Suites: stable
    Components: main
    Architectures: amd64 arm64
    Signed-By: /etc/apt/keyrings/vitrina.asc
    EOF
    sudo apt update
    sudo apt install jkit
    ```

    **A .deb or .rpm.** Download the package for your system from the
    [latest release](https://github.com/adriandeleon/jkit/releases/latest), then:

    ```bash
    sudo apt install ./jkit_*_amd64.deb      # Debian, Ubuntu (arm64: jkit_*_arm64.deb)
    sudo dnf install ./jkit-*.x86_64.rpm     # Fedora, RHEL, Rocky, Alma 9+ (arm64: jkit-*.aarch64.rpm)
    ```

    **Homebrew on Linux** works too:

    ```bash
    brew install adriandeleon/tap/jkit
    ```

    The Linux packages also install bash completion. From 0.5.0, the `.deb` and `.rpm` are signed
    with the Vitrina repository's key; see [verify a .deb or .rpm](#verify-a-deb-or-rpm).
  </TabItem>
  <TabItem label="Windows">
    Windows x64 is a preview: jkit works there, but is less tested than on macOS and Linux.

    **The installer** (from 0.6.0): download `jkit-<version>-windows-x64.msi` from the
    [latest release](https://github.com/adriandeleon/jkit/releases/latest) and open it. It asks
    who jkit is for: *just for you* (in `%LOCALAPPDATA%\Programs\jkit`, on your `PATH`, no
    administrator rights needed) or *all users* (in `%ProgramFiles%\jkit`, on the system `PATH`,
    which asks for administrator rights). Open a new terminal afterwards. The `.msi` isn't
    Authenticode-signed, so SmartScreen may say "Windows protected your PC": check the file
    against `SHA256SUMS` ([below](#verify-a-download)), then choose *More info* → *Run anyway*.

    **winget**:

    ```powershell
    winget install AdrianDeLeon.jkit
    ```

    If winget doesn't find it yet (a new release takes a while to reach the winget catalogue),
    use the `.msi`, or download `jkit-<version>-windows-x64.zip` and put `jkit.exe` in a folder
    on your `PATH`.

    `jkit.exe` needs the Microsoft Visual C++ runtime. The `.msi` installs the runtime's two DLLs,
    `vcruntime140.dll` and `vcruntime140_1.dll`, next to `jkit.exe`, and from 0.5.0 the `.zip`
    carries them too: keep them next to it, in a folder of its own. winget installs the Visual C++
    Redistributable (2015 or newer, x64) along with jkit.

    Windows on ARM runs the x64 build under emulation. See [Windows](/guides/windows/) for what
    works differently.
  </TabItem>
</Tabs>

### Any other system: a plain binary

Each release has a `.tar.gz` (and a `.zip`) per platform: `linux-x64`, `linux-aarch64`,
`linux-x64-musl`, `macos-aarch64` (Apple Silicon) and `macos-x64` (Intel). Each holds `jkit`,
`LICENSE` and `THIRD-PARTY-NOTICES`. Download yours from the
[latest release](https://github.com/adriandeleon/jkit/releases/latest), then put `jkit` anywhere
on your `PATH`:

```bash
tar -xzf jkit-*-linux-x64.tar.gz
sudo install jkit /usr/local/bin/
```

`linux-x64-musl` (from 0.5.0) is a static binary linked against musl, for Alpine and other musl
systems. It needs nothing from the system, so it also runs on glibc distributions older than
2.34. There is no arm64 musl build yet: GraalVM's native-image can't make one.

A jkit installed this way updates itself with [`jkit self-update`](/reference/commands/self-update/).
For Homebrew, apt, dnf and winget, `jkit self-update` prints that tool's upgrade command instead,
and for the Windows `.msi` a command that installs the newer `.msi`.

### From source

Building needs JDK 25, and GraalVM 25 for the native binary. Maven comes through the wrapper.

```bash
git clone https://github.com/adriandeleon/jkit.git
cd jkit
./mvnw verify                                   # build and test on the JVM
GRAALVM_HOME=/path/to/graalvm-25 ./mvnw -Pnative package -DskipTests
sudo install jkit-cli/target/jkit /usr/local/bin/
```

## System requirements

| System | Needs |
| --- | --- |
| Linux (x64, arm64) | glibc 2.34 or newer, and zlib: Debian 12+, Ubuntu 22.04+, Fedora, RHEL, Rocky or Alma 9+. Not Ubuntu 20.04 or RHEL 8. This applies to the Homebrew build too. |
| Linux x64 with musl (Alpine), or glibc older than 2.34 | Nothing: the `linux-x64-musl` build is static. There is no arm64 musl build. |
| macOS (Apple Silicon, Intel) | macOS 14 (Sonoma) or newer (jkit 0.4.0 and earlier: macOS 15) |
| Windows x64 (preview) | The Microsoft Visual C++ runtime: the `.msi` installs its DLLs, the `.zip` carries them (from 0.5.0), and winget installs the Redistributable |

Pre-releases (versions with a hyphen) are on the
[releases page](https://github.com/adriandeleon/jkit/releases) only, not in Homebrew, apt or
winget. A pre-release `.msi` installs as its release version (0.7.0-rc.1 as 0.7.0), and the
release's `.msi` then replaces it.

## Verify a download

Put the file you downloaded in a folder with `SHA256SUMS` and, from 0.4.0, `SHA256SUMS.asc`, both
from the same release, then run the steps below in that folder. With the
[GitHub CLI](https://cli.github.com), one command gets all three:

```bash
gh release download v0.6.0 --repo adriandeleon/jkit -p SHA256SUMS -p SHA256SUMS.asc -p 'jkit-0.6.0-linux-x64.tar.gz'
```

1. Import jkit's release key, `jkit-release.asc` from jkit's repository, once:

   ```bash
   curl -fsSL https://raw.githubusercontent.com/adriandeleon/jkit/v0.6.0/jkit-core/src/main/resources/dev/jkit/core/keys/jkit-release.asc | gpg --import
   ```

2. Check that `SHA256SUMS` is signed by it, as `jkit self-update` does:

   ```bash
   gpg --verify SHA256SUMS.asc SHA256SUMS
   ```

   It must say `Good signature from "jkit release signing key"`, with the fingerprint
   `A944 4E8F 5048 FEBC B942 E110 FC89 EBE6 8C45 39E6`. gpg also warns that the key "is not
   certified with a trusted signature". That only means you haven't signed the key yourself:
   comparing the fingerprint with the one here is the check.

3. Check your file against `SHA256SUMS`:

   ```bash
   sha256sum --check --ignore-missing SHA256SUMS
   ```

   It must print `<file>: OK`. On macOS, use `shasum -a 256 --check --ignore-missing SHA256SUMS`.
   On Windows PowerShell, compare `(Get-FileHash <file>).Hash` with the file's line in
   `SHA256SUMS`.

To check where and how a file was built, without gpg, each one also has a GitHub build
provenance attestation, which the GitHub CLI verifies:

```bash
gh attestation verify jkit-*-linux-x64.tar.gz --repo adriandeleon/jkit
```

### Verify a .deb or .rpm

From 0.5.0, the `.deb` and `.rpm` are signed with the key the Vitrina apt repository signs with,
`8486 A7AF 4FC8 FEE9 3D83 CDB4 EA5F A138 C2C0 9C4A`, published at
https://vitrina-project.dev/vitrina.asc. To check an `.rpm`:

```bash
sudo rpm --import https://vitrina-project.dev/vitrina.asc
rpm -K jkit-*.rpm                           # digests signatures OK
```

Once the key is imported, `dnf` checks the signature of a package it installs from a repository,
but by default not of a package given as a file or URL (`localpkg_gpgcheck`), so run `rpm -K`
first. A `.deb` carries its signature as a `_gpgorigin` member, which `debsig-verify` checks; apt
and dpkg don't check a downloaded `.deb`. Both packages are also listed in `SHA256SUMS`, so the
steps above work for them too. Installing without the key imported works as before.

### SBOM

Each release also carries a CycloneDX SBOM (`jkit-<version>-sbom.cdx.json`), the list of
libraries compiled into jkit. It is made from the Linux x64 build; the other builds compile in the
same libraries, and the macOS x64 binary is built with Liberica NIK instead of GraalVM CE.

## Turn on the shell hook

A program can't change the shell that started it, so to switch versions in your current shell,
jkit needs a small shell function: the hook. It also puts your global versions on `PATH` and sets
`JAVA_HOME`, `MAVEN_HOME`, `GRADLE_HOME`, `SBT_HOME` and `GRAALVM_HOME` in each new shell.

<Tabs syncKey="shell">
  <TabItem label="bash">
    ```bash
    jkit hook --install                  # adds a short marked block to ~/.bashrc
    jkit hook --install --auto-switch    # the same, and switch to a project's versions on cd
    ```

    jkit prints exactly what it added:

    ```console
    $ jkit hook --install
    added the jkit hook to ~/.bashrc:
        # >>> jkit >>>
        # added by jkit hook bash --install; remove with jkit hook bash --uninstall
        __jkit='/usr/bin/jkit'
        if [ ! -x "$__jkit" ]; then __jkit=; IFS=: read -r -a __jkit_p <<< "$PATH"; for __jkit_d in "${__jkit_p[@]}"; do case "$__jkit_d/" in '/home/you/.jkit/'*) ;; *) if [ -x "$__jkit_d/jkit" ]; then __jkit=$__jkit_d/jkit; break; fi ;; esac; done; unset __jkit_p __jkit_d; fi
        if [ -n "$__jkit" ]; then eval "$("$__jkit" hook bash)"; fi; unset __jkit
        # <<< jkit <<<
      file   ~/.bashrc updated
      new bash shells load it; for this one: eval "$('/usr/bin/jkit' hook bash)"
      to also switch to a project's versions on cd: jkit hook bash --install --auto-switch
    ```

    The block runs jkit by its full path (here `/usr/bin/jkit`, from apt), and looks for it on
    `PATH` if it has moved.

    Tab completion comes with the hook. To load it by hand instead, add
    `eval "$(jkit hook bash)"` to `~/.bashrc`.
  </TabItem>
  <TabItem label="zsh">
    ```bash
    jkit hook --install zsh              # adds a short marked block to ~/.zshrc
    jkit hook --install zsh --auto-switch
    ```

    Leave out `zsh` if it's your login shell (`$SHELL`). Tab completion comes with the hook,
    through bashcompinit. To load it by hand instead, add `eval "$(jkit hook zsh)"` to
    `~/.zshrc`.
  </TabItem>
  <TabItem label="fish">
    ```bash
    jkit hook --install fish             # writes ~/.config/fish/conf.d/jkit.fish
    jkit hook --install fish --auto-switch
    ```

    Leave out `fish` if it's your login shell. To load it by hand instead, run
    `jkit hook fish | source`. fish has no tab completion for jkit yet.
  </TabItem>
  <TabItem label="PowerShell">
    `jkit hook --install` doesn't edit PowerShell profiles yet (on Windows it stops and prints the
    line below), so add the hook by hand:

    ```powershell
    notepad $PROFILE
    # add this line, save, and open a new PowerShell window:
    jkit hook pwsh | Out-String | Invoke-Expression
    ```

    Windows PowerShell 5.1 (the one Windows comes with) runs no profile until you allow scripts:
    `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`. PowerShell 7 allows them already.

    PowerShell doesn't switch on `cd` yet. For programs started outside a hooked PowerShell
    (cmd.exe, IDEs) to follow `jkit use … --global` too, run `jkit env --install` once; see
    [Windows](/guides/windows/#programs-outside-powershell).
  </TabItem>
</Tabs>

Then open a new terminal window. `jkit hook --uninstall` takes the block out again. The
[shell hook reference](/reference/shell-hook/) has the details.

<Aside type="tip">
You don't need the hook for `jkit use … --global`, `jkit pin` or `jkit exec`, so CI jobs and
scripts can skip it. See [CI](/guides/ci/) and [scripts](/guides/scripts/).
</Aside>

## Check it worked

In the new window:

```bash
jkit --version
jkit doctor
```

[`jkit doctor`](/reference/commands/doctor/) checks the hook, `PATH`, links, installs and the
project file, says how to fix each problem it finds, and changes nothing. Before your first JDK
it looks like this:

```console
$ jkit doctor
ok    jkit 0.6.0, linux-x64, home ~/.jkit
info  ~/.jkit doesn't exist yet; the first install creates it
ok    shell hook loaded (bash)
ok    jkit on PATH: /usr/bin/jkit
ok    default vendors: temurin (jdk, default), graalvm-ce (graalvm, default); not checked against foojay: no cached vendor list yet
ok    global links and this shell's choices point at existing installs
ok    no *_HOME variable set outside jkit
ok    0 installs, nothing left over
info  no project file here or above (jkit.toml, .jkit.toml, .sdkmanrc, .tool-versions, .java-version)
info  no version index cached yet; search and install fetch it
info  no active JDK to try
no problems found
```

A `warn` or `fail` line is followed by a `fix:` line saying what to do. `jkit doctor` exits 1 when a check fails.

Now install a JDK: the [quickstart](/start/quickstart/) walks through it.
