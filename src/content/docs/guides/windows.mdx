This page covers everything that is different on Windows. jkit runs on Windows x64, but this part
is a **preview**: it is less tested than macOS and Linux, and a few things work only by hand. If
something breaks, please [open an issue](https://github.com/adriandeleon/jkit/issues).

What works the same: `search`, `install`, `upgrade`, `list`, `status`, `env`, `exec`, `pin`,
`sync`, `doctor`, `remove`, `prune`, `config` and `self-update`, and `use` in a PowerShell with the
hook loaded.

What is different, in short:

- The hook goes into your PowerShell profile **by hand**; `jkit hook --install` doesn't edit
  PowerShell profiles yet, and prints the line to add. Windows PowerShell 5.1 also needs scripts
  allowed first ([see below](#load-the-hook-in-powershell)).
- PowerShell doesn't switch versions on `cd` yet. Run `jkit sync` in a project instead.
- cmd.exe and IDEs see the global JDK once you run `jkit env --install`
  ([see below](#programs-outside-powershell)).
- Git Bash, MSYS2 and Cygwin have no jkit hook.
- Windows on ARM runs the x64 build under emulation.

## Install

With winget:

```powershell
winget install AdrianDeLeon.jkit
```

The winget package appears once winget-pkgs has merged the release. Until then, or if you prefer,
use the `.zip`:

<Steps>

1. Download `jkit-<version>-windows-x64.zip` from the
   [releases page](https://github.com/adriandeleon/jkit/releases/latest). It holds `jkit.exe`,
   `LICENSE`, `THIRD-PARTY-NOTICES` and, from 0.5.0, the Visual C++ runtime's
   `vcruntime140.dll` and `vcruntime140_1.dll`.

2. Check it against the release's `SHA256SUMS`:

   ```powershell
   Get-FileHash .\jkit-0.5.0-windows-x64.zip -Algorithm SHA256
   ```

   The hash must match the line for that file in `SHA256SUMS` (PowerShell prints it in
   uppercase; compare without regard to case).

3. Unpack `jkit.exe` and the two DLLs into a folder of their own, such as
   `%LOCALAPPDATA%\Programs\jkit`, and add
   that folder to your user `Path` (search the Start menu for "Edit environment variables for
   your account").

4. Open a new PowerShell and check: `jkit --version`.

</Steps>

`jkit.exe` needs the Microsoft Visual C++ runtime. winget installs the Visual C++
Redistributable (2015 or newer, x64) along with jkit. The `.zip` carries the runtime's two DLLs:
keep them next to `jkit.exe`. `jkit self-update` keeps them up to date. Once the Redistributable
is installed you can delete the two DLLs, and Windows Update keeps the runtime patched. With
jkit 0.4.0 and earlier, whose `.zip` has no DLLs, install the Redistributable first:

```powershell
winget install Microsoft.VCRedist.2015+.x64
```

## Load the hook in PowerShell

The hook puts the global versions on `PATH`, sets `JAVA_HOME` and friends, and lets `jkit use`
change the current PowerShell. Add it to your profile by hand:

```powershell
if (-not (Test-Path $PROFILE)) { New-Item -ItemType File -Path $PROFILE -Force }
notepad $PROFILE
```

Add this line, save, and open a new PowerShell:

```powershell title="Microsoft.PowerShell_profile.ps1"
jkit hook pwsh | Out-String | Invoke-Expression
```

PowerShell 7 (`pwsh`) and Windows PowerShell 5.1 have separate profiles; add the line to each one
you use. `jkit hook --install` (and `jkit hook pwsh --install`) stops with an error that prints
this same line.

The hook puts the global `bin` folders first on `PATH`, ahead of the system `PATH`, where
`jkit env --install` alone can't put them.

Windows PowerShell 5.1 (the one Windows comes with) runs no profile, and no script, until you allow
them, so the hook never loads. Allow them once for your account; PowerShell 7 allows them already:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

Then:

```powershell
jkit install jdk@21        # the first JDK becomes the global default
java -version
jkit use jdk@17 zulu       # only this PowerShell (after jkit install jdk@17 zulu)
jkit status
```

Without the hook, `jkit use` without `--global` can't change the shell, and says so.

**Git Bash.** jkit has no hook for Git Bash, MSYS2 or Cygwin. An older jkit's
`jkit hook --install` could add a bash block to Git Bash's `~/.bashrc`, which made every Git Bash
start fail; `jkit hook bash --uninstall` takes it out.

## Projects in PowerShell

Switching on `cd` isn't available in PowerShell yet. In a project with a `jkit.toml` (or
`.sdkmanrc`, `.tool-versions`, `.java-version`), run:

```powershell
jkit sync                  # installs the pins and switches this PowerShell to them
```

`jkit exec` works with or without the hook: `jkit exec -- mvn -v`. On Windows it looks for
`.exe`, `.cmd` and `.bat` files on the `PATH` it gives the command, so `mvn` runs `mvn.cmd`. A
path is resolved against the folder the command runs in and tried the same way, so
`jkit exec -- ./gradlew build` runs `gradlew.bat`.

For a script, load the environment once:

```powershell
jkit env --shell pwsh | Out-String | Invoke-Expression
```

## Programs outside PowerShell

`jkit use jdk@21 --global` points `%USERPROFILE%\.jkit\global\jdk` at the install. Only shells
with the hook read it on their own. For cmd.exe, IDEs and anything else started from Explorer, run
once:

```powershell
jkit env --install
```

It sets `JAVA_HOME`, `MAVEN_HOME`, `GRADLE_HOME`, `SBT_HOME` and `GRAALVM_HOME` in your user
environment to jkit's global links, for each tool that has a global version, and puts their `bin`
folders first on your user `PATH` (`GRAALVM_HOME` doesn't go on `PATH`). The rest of `PATH` stays
exactly as it was, `%VAR%`s and all. Each change is printed. Programs started from then on get the
variables (a new terminal, an IDE you restart); running ones, this shell included, keep what they
have.

From then on, `jkit use … --global` changes the version for all of them, with no need to touch the
variables again: they name the global links, which `jkit use` moves. `jkit use … --global` says
whether programs outside PowerShell follow it. A tool that has no global version yet is left out;
after you set one, run `jkit env --install` again.

- **A `*_HOME` of your own** that `--install` replaces is kept in `JKIT_SAVED_<TOOL>` (such as
  `JKIT_SAVED_JDK`), and `jkit env --uninstall` puts it back. A value that is one of jkit's own
  installs isn't kept.
- **`jkit env --uninstall`** removes only what `--install` set. It doesn't put back a folder that no
  longer exists, and says so.
- **The system `PATH` comes first.** Windows puts the system `PATH` before the user one, so a
  `java` there (from a JDK installed for all users, say) still wins outside a hooked PowerShell.
  `jkit env --install` and `jkit doctor` warn about it; removing it from the system `PATH` needs
  admin rights. A hooked PowerShell puts the global versions first anyway.
- **`jkit doctor`** says whether your user environment is set up (check `user-env`), and which
  variables are missing.

To point an IDE at a JDK directly, see [IDEs](/guides/ides/).

## Files and folders

| Path | What |
| --- | --- |
| `%USERPROFILE%\.jkit\tools\` | installed JDKs, Maven, Gradle and sbt |
| `%USERPROFILE%\.jkit\global\` | the global defaults, as directory junctions |
| `%USERPROFILE%\.jkit\index\` | cached version lists |
| `%USERPROFILE%\.jkit\config.toml` | settings |

The global links are directory junctions, which need neither admin rights nor Developer Mode.
Next to each one, a small `.<name>.target` file (such as `.jdk.target`) records where it points,
so jkit can still report a link whose install is gone.

`JKIT_HOME` moves everything and must be an absolute path, such as `D:\jkit`. On Windows there are
no POSIX owners, so the ownership checks jkit makes on Linux and macOS don't apply; the default
permissions of your user profile protect `%USERPROFILE%\.jkit`. See
[Shared machines](/guides/shared-machines/).

## Updating jkit

```powershell
jkit self-update --check     # is a newer jkit out?
jkit self-update
```

A jkit from winget is left to winget, and `self-update` prints the command:
`winget upgrade AdrianDeLeon.jkit`. A jkit from the `.zip` is replaced in place after checking the
download against the release's `SHA256SUMS`, signed by jkit's release key; the Visual C++ DLLs
next to it are replaced too, and never added to a folder without them. Windows can't replace a
running `.exe`, so the old one is renamed to `jkit.exe.old` and deleted by the next
`self-update`. If an older jkit that is still running holds `jkit.exe.old`, the old binary is set
aside as `jkit.exe.1.old` (and so on), and the next `self-update` deletes them all.

## Windows on ARM

There is no native ARM build yet: winget installs the x64 build, which runs under Windows'
x64 emulation. jkit then sees an x64 system, so the JDKs it installs are x64 builds and run under
emulation too.

## Known rough edges

- **Antivirus.** Scanners can hold files that were just unpacked. jkit retries the final step of
  an install for a while; a slow install right after a download is usually the scanner.
- **Removing an install that is in use.** `jkit remove` moves the folder aside first, so when
  something still has it open (an IDE, a Gradle daemon) nothing is touched and it says so. Stop
  the program (`gradle --stop` for the daemon) and run it again.
- **Paths with spaces** in `JAVA_HOME` set outside jkit, such as `"C:\Program Files\…"` with
  quotes, are read without the quotes.
- **Console symbols.** Where the console's code page lacks jkit's symbols, jkit shows `->`, `...`,
  `+`, `o` and `*` instead of `?` (as with `LANG=C` elsewhere), and `--json` writes `\u` escapes.
  Paths with accents (`C:\Users\José`) reach the PowerShell hook and `jkit env --shell pwsh`
  intact from 0.5.0.

## Uninstall

```powershell
jkit env --uninstall                               # if you ran jkit env --install
notepad $PROFILE                                   # remove the jkit hook line
Remove-Item -Recurse -Force "$env:USERPROFILE\.jkit"
winget uninstall AdrianDeLeon.jkit                 # or delete jkit.exe and its DLLs from its folder
```

Remove any `JAVA_HOME` and `Path` entries you added by hand, too.
